Security model#

This is a single-administrator homelab that happens to be reachable from the internet. The design goal is that nothing at home accepts an inbound connection, every published hostname has an identity check in front of it, and no credential that matters sits in Git or on the NAS in a readable form. This page walks the trust boundaries from the outside in, and ends with the risks that are accepted on purpose.

The edge#

No inbound ports. The router forwards nothing. Web traffic arrives over a tunnel that cloudflared opens outwards, and game traffic over a link that frpc opens outwards (Networking and ingress). The home IP address is in no DNS record.

Access in front of every hostname. A wildcard Access application makes *.gkcluster.org owner-only, and cloudflare/access_guard.tf fails tofu plan if any tunnelled or proxied hostname is not covered by an application that asks for an identity or a service token. The only exceptions are the hostnames flagged access_bypass = true in cloudflare/locals.tf: pages (public static pages) and ntfy (its own token authentication). The guard works in both directions, so an application that lets everyone in cannot be pointed at a hostname that is not on that list. Details: Authentication.

One rate-limit rule. The Free plan allows a single rule, and it is spent on ntfy, the one service whose own login faces the internet (cloudflare/waf.tf): about 100 requests a minute per client on ntfy’s paths, then a 10-second block. The Free plan cannot match on hostname, so the rule matches those paths on every host; a new service must not use a path that starts with a topic name or /v1/.

The VPS relay publishes only what is listed. frps on the VPS accepts only the ports in its allowPorts, which mirror vps_relay.forwards (today the Minecraft game range, 30565-30584). Its control port listens on the VPS’s tailnet address only, the tailnet policy lets the relay’s tag reach that one port and nothing else, and the relay pod advertises no routes. The VPS has no way to open a connection into the house. Plain-text RCON (30600-30619) is never forwarded.

The cluster#

Scheduling and delivery#

  • The control plane runs no workloads. node02 carries node-role.kubernetes.io/master:NoSchedule, so application pods never share a node with etcd and the API server. node03, the warm standby, has only a soft PreferNoSchedule taint.

  • ArgoCD can only deploy from an allow-list. The kubernetes AppProject (argo-cd/argo-project.yaml) restricts sourceRepos to this repository, the scrap repository and the named Helm registries the services use. Someone with ArgoCD admin rights cannot point an Application at an arbitrary repository. The project does allow every namespace and every cluster-scoped kind: it is the cluster’s own platform project, not a tenant sandbox.

  • The ArgoCD admin account is disabled. All logins go through Dex and GitHub.

  • No admission policy engine. Kyverno is present in the repository but switched off (enable_kyverno: false); no policies were in use.

Pod security#

There is no cluster-wide Pod Security Standard, because a handful of system workloads genuinely need privilege. Security contexts are set per workload. The workloads this repository writes the pod spec for are non-root with every capability dropped; two upstream charts (Headlamp, argocd-monitor) are left at their weaker defaults.

Headlamp is a known soft spot. Its ServiceAccount is bound to cluster-admin by the chart, and the token that just headlamp-token mints for the login page lasts 100 days. Anyone who gets past Access and oauth2-proxy and holds that token has the whole cluster.

Images and charts#

Every image and chart is pinned to a version tag in Git, never latest. Renovate (renovate.json) watches the Application templates and the manifests under kubernetes-services/, opens a pull request for each new version, and merges Helm chart bumps automatically, except Cilium’s: a Cilium bump restarts the CNI agent on every node, so its pull requests wait for a person.

A few pins carry an extra, manual rule: when chosen, the version was the newest release at least two weeks old, as a buffer against a compromised release. That applies to ntfy, the Jellyfin chart and image, and the rclone, age and SQLite tools the backup jobs use. Renovate still offers newer versions for these; the rule is recorded beside each pin and kept by hand. Tools that are downloaded at run time (age, the Headlamp ArgoCD plugin) are checked against a SHA-256 in values.yaml and the pod fails if it differs.

Three properties of Cilium’s enforcement are worth knowing:

  • It always admits traffic from a pod’s own node. Kubelet probes keep working under a deny-all rule, but so do host-network pods on that node.

  • CIDR rules match node addresses, because the chart sets policyCIDRMatchMode: [nodes] (Cilium’s default is never to). The RCON rule depends on it: it excludes the cluster nodes’ addresses from the LAN range (minecraft.worlds.rcon_allowed_cidrs), so host processes on other nodes cannot reach RCON from their LAN addresses (through Cilium’s tunnel they carry a node identity, which no CIDR rule matches). A node that joins the cluster must be added to the exclusion list. Build tools run on the hosts of nuc2 (the world node, admitted as a pod’s own node) and ws03. ws03’s connection arrives through Cilium’s tunnel from its Cilium address, which no CIDR rule matches, so a CiliumNetworkPolicy admits it by node name (fromNodes, minecraft.worlds.rcon_allowed_nodes), with nodeSelectorLabels: true in the Cilium values.

  • A pod that reaches a NodePort keeps its own pod identity: with no kube-proxy there is no SNAT to the node’s address on the way. No CIDR rule matches a pod, so pods are refused RCON unless a rule names them (the dashboard’s).

The backups-egress rule works by name: the backup pods’ DNS queries go through Cilium’s DNS proxy, which learns the addresses behind the allowed names and opens only those. just hubble observe -n backups --verdict DROPPED (or the Hubble UI) shows what it refused.

The ntfy and scrap policies limit who reaches the pod directly. Anything that can reach Cilium’s Gateway can still reach them through it, which is why ntfy’s tokens and the oauth2-proxy check are the real gates.

The nodes#

  • SSH is by key, to one account. Ansible connects as ansible, an account with no password and passwordless sudo, whose authorised keys come from pub_keys/ansible_rsa.pub. Only the public key is in Git. The private key stays on the operator’s machine and reaches the devcontainer through VS Code’s forwarded SSH agent, so it is never copied into the container.

  • Nodes patch themselves. unattended-upgrades installs packages, kernels included, from 00:00; system-upgrade-controller applies K3s patch releases from 01:00; kured drains and reboots one node at a time between 02:30 and 05:00 when a reboot is pending (Automatic maintenance). ws03 is the exception: it is a desktop, keeps its own update policy, and no automation reboots it.

  • Multipath TCP is off on every node (net.mptcp.enabled=0, in /etc/sysctl.d/90-disable-mptcp.conf), as a mitigation for a kernel MPTCP vulnerability (CVE-2026-98432). Nothing in the cluster uses MPTCP. Ansible sets it, not the kernel-settings DaemonSet, because that DaemonSet cannot run on the tainted nodes. ansible-playbook pb_all.yml --tags sysctl applies it alone.

  • A corrected containerd AppArmor profile is loaded before K3s starts (roles/k3s/tasks/apparmor.yml). Ubuntu 25.04 and later stack container profiles with unconfined, and containerd’s stock profile then denies every signal sent inside a container: nginx reloads, graceful shutdowns, Go’s preemption. The role ships containerd’s template with the extra peer rule, so containers stay confined and signals work again.

Secrets#

Nothing secret is in Git in a readable form.

        flowchart LR
    plain["Plain value<br/>on the operator's machine"]
    kubeseal["kubeseal<br/>encrypts with the controller's public key"]
    git["SealedSecret in Git<br/>*-secret.yaml"]
    argo["ArgoCD sync"]
    ctrl["sealed-secrets controller<br/>holds the private key"]
    secret["Secret in the namespace"]
    pod["Pod"]

    plain --> kubeseal --> git --> argo --> ctrl --> secret --> pod

  • Sealed Secrets. Each credential is encrypted with kubeseal against the controller’s public key and committed as a SealedSecret. Only the controller, in kube-system, can turn it back into a Secret, and a sealed value is bound to its name and namespace. Procedures and the full list: Manage Sealed Secrets.

  • Automatic key renewal is off (keyrenewperiod: "0" in kubernetes-services/templates/sealed-secrets.yaml). Renewal only adds a key: it retires nothing and re-encrypts nothing, so it bought no security, and it made every offline key backup stale within a month. The key is rotated by hand instead (Rotate the key by hand).

  • The sealing keys are backed up, encrypted. The nightly etcd backup on the control plane also exports them, age-encrypted, to the NAS (Sealed Secrets key backup). With that file and the repository, a dead cluster’s secrets can be recovered.

  • One secret is created out of band. admin-auth, Grafana’s built-in administrator account, is set with just set-admin-password and never committed.

  • The backups cannot be read by anything that holds them. etcd snapshots contain every Secret in plain text, so every backup is encrypted with age to a public key (etcd_backup_age_recipient, and the same key in offsite_backup.age_recipient; a pre-commit hook checks they match). The private key is kept offline by the owner. The cluster, the NAS and Google Drive hold only ciphertext (Backups and disaster recovery).

  • The Cloudflare state is encrypted too. OpenTofu’s state file holds the tunnel secret and the Access email lists; it is local, gitignored and encrypted with a passphrase.

  • gitleaks runs in pre-commit with the default rules. .gitleaks.toml allow-lists files named *-secret.yaml (singular), which is where the encrypted SealedSecrets live. A file named *-secrets.yaml is not allow-listed and is blocked.

Operator tooling#

Day-to-day operation is done by Claude Code inside the devcontainer, and it runs only inside claude-sandbox: a bwrap jail with no SSH agent, no ~/.ssh, and a network egress filter that reaches private addresses only if they are listed (the nodes, the BMC and the NAS). It holds its own SSH key for the ansible account, which just claude-ssh-bootstrap revoke removes from every node. The full account is on Claude Code integration.

Accepted risks#

These are known and left as they are.

  • One control plane. node02 holds the only etcd member. Its loss stops the API, though running pods keep serving, until it is restored onto node03 from the nightly backup (Recover the control plane). Three RK1 servers would spend memory the 8 GB nodes do not have.

  • The Headlamp token is cluster-admin, lasts 100 days, and is pasted into a browser. It is protected by Access and oauth2-proxy and by nothing else.

  • The Drive token can delete what it uploaded. rclone’s drive.file scope lets it see and change only its own files, but that includes deleting them. Someone who takes over the cluster cannot read the off-site backups, but could destroy the Drive copy, and with root on the cluster the NAS copies too. The second off-site copy covers this (Second off-site copy: Backblaze B2, ADR 14): the NAS backups also go to a Backblaze B2 bucket under Object Lock in compliance mode, where no key, the account owner’s included, can delete or overwrite a version for 30 days. The Minecraft tarballs and archive stay on Drive only (the archive has other copies). This holds once offsite_backup.b2.enabled is on.

  • Pinned workloads go down with their node. Grafana and Prometheus (node04), and Jellyfin and the Minecraft worlds (nuc2), have no replica. That is the price of not running replicated storage (Storage).

  • The LAN is trusted more than the internet. The Gateway answers on the node addresses, on the LAN and the tailnet, without Cloudflare Access in front. The in-cluster login still applies, but the services with no login at the Gateway (home, echo) are open to any device on the LAN, and Jellyfin and RCON are LAN services by design.

  • No default-deny between namespaces. A compromised pod can reach most other Services in the cluster.

  • NFS trusts its clients. The NAS’s exports take a client’s word for its uid (AUTH_SYS, no Kerberos). A host allowed to mount an export can read and write anything in it as any uid but root (squashed to 65534, except on /k8s-dynamic, where the NFS CSI driver needs root), so a compromised node, or a privileged pod on one, reaches every service’s files on the NAS, backups included. The nas role admits only the nodes and ws03, gives the nodes only the exports the cluster mounts (the media library read-only), keeps ws03’s desktop mount out of the cluster’s data (/bigdisk/k8s-cluster is the nodes’ alone), and owns each backup directory by its one writer (Build or rebuild the NAS (Ubuntu Server + ZFS)).

  • Viewer rules are only as narrow as their values. The guard detects an open policy, not a wide one, such as a public email domain in viewer_email_domains.
