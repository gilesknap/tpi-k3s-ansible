Build or rebuild the NAS (Ubuntu Server + ZFS)#

The NAS, gknas at 192.168.1.3, is a QNAP TS-253D (Celeron J4125, 32 GB RAM, two bays, two 2.5GbE ports). On 17 November 2026 it moved from QTS, QNAP’s own OS, to Ubuntu Server 26.04 with ZFS, configured by Ansible like the rest of the estate. It is not a cluster node: pb_nas.yml configures it, separately from pb_all.yml, and nothing in pb_all.yml reaches it.

Note

This page describes the NAS and how to build it again from bare metal. The cluster’s directories on the NAS lists the directories the cluster mounts on it. Its notes on QTS describe the move from it.

How the exports differ from QTS#

Every consumer mounts NFS 4.1 by the paths above (vers=4.1 or nfsvers=4.1 on each PV and storage class, and on node02’s etcd backup mount). QTS served those paths from an NFSv4 pseudo-root (/share/NFSv=4/bigdisk); Ubuntu exports the real directories, which are the same paths, so the clients see no difference.

nas_nfs_clients in the role’s defaults holds the client list, and each entry of nas_nfs_exports can narrow it (clients) or make it read-only to some hosts (read_only_for). A new node must be added there (and the playbook re-run) before its pods can mount anything from the NAS. The nodes still reach /bigdisk/k8s-cluster and /bigdisk/media without /bigdisk itself being exported to them: the server’s NFSv4 pseudo-root shows them the path down to the exports they are given, and nothing else in it.

ws03’s desktop mounts gknas:/bigdisk on /media/private/bigdisk, for the media library and the photo archive. It is not given the cluster’s own data: /bigdisk/k8s-cluster is exported to the nodes alone (ws03 is a node too, but its workstation taint keeps every pod that mounts it off ws03), so /media/private/bigdisk/k8s-cluster on ws03 is only the empty directory the dataset mounts over on the NAS. Read or copy the cluster’s files on the NAS itself (ssh nas, with sudo for scrap’s), as Backup and restore does. The photo archive is read-only to ws03: it changes only by hand, on the NAS.

On QTS the backup directories were 0777, because several uids write them. Here each is owned by its one writer, mode 0755: Grafana’s backups by 472, Jellyfin’s by 122:124, and etcd/ (with pre-upgrade/) by 65534, which node02’s root-run job is squashed to. Only that writer can add or delete backups there (pruning older files of other owners included), and the off-site copy, which reads backups/ as 65534, can still read them all. backups/scrap-curated/ becomes 0750, scrap’s alone, like its other directories.

Two things follow from moving NAS:

  • File handles change. A pod that held an NFS mount across the switchover has a stale handle and must be restarted. The migration stops every NFS user first, so this only matters for anything missed.

  • The NAS must keep its IPv4 address. Every consumer names 192.168.1.3 and the exports admit clients by IPv4 address. A client that reaches the NAS by name over IPv6 (gknas.lan may get an AAAA record once Ubuntu takes a SLAAC address) is refused: use the address.

Build the NAS from bare metal#

You need: the NAS, a USB stick, the OS NVMe on its PCIe adapter and the devcontainer on ws03.

1. Install Ubuntu#

The install runs on its own once you pick the install stick’s Install gknas entry (Install Ubuntu from the install stick). It creates:

  • hostname gknas, DHCP (the router reserves 192.168.1.3 for it);

  • the ansible account with passwordless sudo, no password, and the keys in pub_keys/ansible_rsa.pub plus the Claude sandbox’s key;

  • the whole of the disk with serial 26100800643000458 (model Fanxiang S500Pro 256GB) as the OS disk. The install refuses unless exactly one disk has that serial and model and one of the NAS’s ports has its MAC (enp3s0 or enp2s0).

nas_os installs the NAS’s packages (ZFS, smartmontools and the rest) in step 2.

Plug a keyboard and screen into the NAS for the install: you pick the stick in the firmware’s boot menu and the entry in the stick’s menu.

The rear panel has one blue USB 3 port and two black USB 2 ports; the front port is USB 3. The firmware setup opens with Del at power-on.

  1. Power the NAS off. Pull both drive trays and unplug the LaCie. The guard would refuse to install onto them, but with them out no mistake can reach them.

  2. Plug the install stick into a USB port, power on, and boot the stick in UEFI mode (its UEFI: entry in the boot menu). Booted the legacy way, it shows no host entries. Pick Install gknas: the install runs on its own and powers off.

  3. Remove the stick and power on. In the firmware setup, put the NVMe’s UEFI entry first in the boot order, before the DOM (QTS).

The NAS has two 2.5GbE ports, enp2s0 and enp3s0; the install takes DHCP on whichever is cabled. The router’s reservation for 192.168.1.3 is by enp3s0’s MAC address, so cable that port (ip -br link on the NAS shows each port’s name and MAC). The installer’s netplan configures both ports under one en* match, so every boot waits two minutes for the port with no cable and then logs systemd-networkd-wait-online as failed; nas_os replaces it with one entry per port (nas_netplan_ethernets), each matched by its MAC address (so a renamed port still gets its configuration), both on DHCP, the one not cabled optional. The role never runs netplan apply: netplan is a systemd generator, so the new configuration reaches networkd at the next daemon-reload followed by a networkd restart or reload, or at the next boot. enp3s0’s configuration is equivalent to the installer’s, so at most its DHCP lease is renegotiated. On other hardware, set the MAC addresses first.

2. Configure the OS, before the data disks go in#

From the devcontainer:

ansible-playbook pb_nas.yml --tags known_hosts
ansible-playbook pb_nas.yml --tags nas_os,nas_fan

nas_os stops Ubuntu assembling the Linux RAID it would find on disks that come from QTS, so do it before the trays go in. udev assembles an array as its disks appear (mdadm --incremental); AUTO -all in /etc/mdadm/mdadm.conf stops that. The initramfs plays no part: Ubuntu 26.04 builds it with dracut, whose host-only image has no mdadm at all while the root is not on md, so it cannot assemble an array before the root is mounted. nas_fan builds the qnap8528 driver (see Fans and the embedded controller).

3. Put the disks in and name them#

Power off, insert both trays (and the LaCie, if it is to become the backup pool), and power on. Then, on the NAS:

ls -l /dev/disk/by-id/ | grep -v -- -part

Set nas_pool_disks (the two ata-Samsung_SSD_870_QVO_4TB_<serial> paths) and nas_backup_pool_disks (the LaCie’s usb-... path) in roles/nas/defaults/main.yml, through a pull request as usual.

4. Create the pools#

Creating a pool destroys everything on its disks, so the role does it only when told, and checks first. It refuses unless:

  • the pool does not already exist, imported or on the disks (an existing pool is imported instead, which changes nothing);

  • the disks are given by /dev/disk/by-id/ path (two for the mirror);

  • no partition of the disks is mounted or used as swap (never overridable);

  • the disks are blank: no partition table, partitions or filesystem signature, unless -e nas_force=true is also given.

Nothing else in the role destroys data: no task destroys a pool, dataset or snapshot (sanoid prunes only snapshots past their retention, and never the held weekly, The hold on the newest weekly snapshot). scripts/check-no-destroy, run by just check, fails if one does, if this gating is removed, or if a cluster playbook targets the NAS. It reads every task’s whole command (argv lists and shell blocks included), the zfs, zpool, filesystem and file modules, and the scripts the roles install; it cannot see a command or path built from variables at run time (rm -rf "$dir"), so it catches mistakes rather than proving the negative. scripts/test-check-no-destroy checks that it catches each case it should.

# The main pool. Disks from QTS carry its RAID, so they need nas_force.
ansible-playbook pb_nas.yml -e nas_create_pool=true -e nas_force=true

# The backup pool, on the LaCie. It is not blank (NTFS), so it needs nas_force.
ansible-playbook pb_nas.yml -e nas_create_backup_pool=true -e nas_force=true

Then the same run creates the datasets, the cluster’s directories (nas_directories: the directories of The cluster’s directories on the NAS, the backup directories owned by their writers as above), the exports, the snapshot schedule and the health checks. Every later run is plain ansible-playbook pb_nas.yml; --check --diff shows what it would change.

5. Put the data back#

From the backup pool or Drive: see Recovery.

6. Monitoring#

nas.monitoring.enabled is true in kubernetes-services/values.yaml (Monitoring), so Prometheus scrapes the NAS as soon as node-exporter answers on it. Set it to false while the NAS is down for longer than NasDown should report.

Running it#

  • Updates install every night (unattended-upgrades, from -security and -updates), kernels included. The NAS never reboots itself, and kured does not manage it. When /var/run/reboot-required exists, reboot it by hand at a quiet time: the cluster’s NFS volumes hang (hard mounts) until it is back, and then carry on.

  • The OS disk is spared writes: the journal is in RAM only (lost on a reboot; capped at 128 MB), / is mounted noatime, and there is no swap.

  • Snapshots: sanoid snapshots every dataset of tank hourly (kept 48), daily (30), weekly (8, on Mondays at 23:30) and monthly (12). A file can be read back from <mountpoint>/.zfs/snapshot/<snapshot>/ on the NAS. The newest weekly snapshot of each dataset is held (The hold on the newest weekly snapshot).

  • The copy to the backup pool: nas-replicate.timer runs syncoid at 06:30, after the cluster’s nightly backups, sending every dataset of tank to backup/tank (incrementally). The copies are read-only, mounted under /srv/backup (/srv/backup/tank/bigdisk and so on), and sanoid keeps 60 daily and 24 monthly snapshots of them (and prunes the weeklies that arrive). backup and backup/tank themselves hold no files and are not mounted (canmount=off): read-only, they could not hold the mount points below them, so those are plain directories on the OS disk. journalctl -u nas-replicate shows the last run.

  • Scrubs: zfs-scrub-monthly@tank.timer and zfs-scrub-monthly@backup.timer (Ubuntu’s own cron scrub is turned off per pool with the org.debian:periodic-scrub=disable property).

  • SMART: smartd watches every disk, with a short self-test daily and a long one on Saturdays: the SSDs as plain SATA, the OS disk as NVMe, and the LaCie through an entry the role adds to /etc/smart_drivedb.h, by USB ID. The LaCie (059f:1106) is a SATA disk behind a SAT bridge (-d sat), which smartmontools’ own database does not know at all. The file also has an entry for the OS NVMe’s old JMicron USB enclosure (152d:0562), an NVMe bridge (-d sntjmicron) that the database takes for a SATA bridge, in case the NVMe goes back in it. smartd scans for disks when it starts, so a disk plugged in later is watched from its next restart. By hand: sudo smartctl -a /dev/nvme0n1.

  • The power button ignores a short press, so knocking it no longer shuts the NAS down (power_key_ignore: true on gknas in hosts.yml; a logind drop-in, /etc/systemd/logind.conf.d/90-power-key.conf). To shut it down from the button, hold it for about 4 seconds, which cuts the power without a clean shutdown; prefer sudo poweroff over SSH.

  • IPMI: openipmi, pulled in by node-exporter’s collectors through ipmitool, is masked (and its failed state cleared): the TS-253D has no BMC, so it only failed at boot.

  • The off-site copy to Google Drive is unchanged: the cluster’s offsite-backup CronJob reads the NAS over NFS (Off-site copy to Google Drive).

The hold on the newest weekly snapshot#

Each dataset sanoid snapshots (nas_hold_datasets: every dataset of tank in nas_datasets, Photos-Archive included) keeps a ZFS hold, tag nas-keep (nas_hold_tag), on its newest weekly snapshot. ZFS refuses to destroy a held snapshot, so a mistyped zfs destroy of that snapshot fails, and so does a zfs destroy -r of the dataset: ZFS destroys a dataset’s snapshots in one all-or-nothing batch before the dataset itself, so neither the dataset nor any of its snapshots goes. (A child dataset with no held snapshot, made by hand or too new to have a weekly, is not protected.) It guards against accidents only. Root can release the hold and then destroy (and zfs destroy -d marks a held snapshot to go as soon as it is released); zpool destroy ignores holds altogether. The backup pool, and the off-site copy, are what cover a deliberate attack.

nas-hold.timer runs /usr/local/sbin/nas-hold daily at 02:00 (nas_hold_on_calendar), after sanoid’s Monday 23:30 weekly: it holds the newest weekly first, then releases the tag from older snapshots, so a dataset never goes without a held snapshot. Other tags are left alone, and running it again changes nothing. The hold costs no space: sanoid keeps that snapshot anyway. The received copies on the backup pool are not held (zfs send does not carry holds).

sanoid prunes weeklies oldest first and only while more than weekly remain, so it never tries to prune the newest one; the role refuses a weekly retention below 1 for a held dataset. If sanoid ever met a held snapshot, its destroy would fail and it would log could not remove <snapshot> and carry on with the rest, trying again on each run.

To see or lift the holds by hand, on the NAS:

# Every snapshot of a dataset with its hold count, then the holds on one.
zfs list -t snapshot -d 1 -o name,userrefs tank/bigdisk/k8s-cluster
zfs holds tank/bigdisk/k8s-cluster@autosnap_<date>_weekly
# Release it, e.g. to destroy that snapshot on purpose.
sudo zfs release nas-keep tank/bigdisk/k8s-cluster@autosnap_<date>_weekly

The next run of nas-hold holds the newest weekly again: to keep a dataset out for good, take it out of nas_hold_datasets.

Monitoring#

node-exporter runs on the NAS on port 9100, with its ZFS collector (pool states), the smartmon collector, and three textfile metrics files the role adds (below). The packaged smartmon.sh stops at the first disk type it does not know, and the OS disk’s sntjmicron came first while it was in its USB enclosure, so on its own it reported only that disk; the role runs an edited copy, /usr/local/sbin/nas-smartmon, that reports every disk (smartmon_device_smart_healthy for each). The role’s own files are nas_zpool.prom (every 5 minutes: each pool’s size and allocated bytes from zpool list, its error counts, and its last finished scrub, kept through a resilver or a scrub in progress), nas_replicate.prom (the last copy to the backup pool) and nas_hold.prom (nas_zfs_held_snapshot_timestamp_seconds{dataset}, the creation time of each dataset’s held weekly snapshot, and whether nas-hold last succeeded).

Some start working later than the rest, because their metrics are absent until there is something to measure (an absent metric fires nothing):

  • NasPoolFillingUp, once the NAS runs the version of nas-zpool-metrics that exports pool size and allocation: re-apply pb_nas.yml after a change to the role’s metrics, as the rules and the metrics ship separately.

  • NasZfsScrubErrors and NasZfsScrubOverdue, after a pool’s first scrub (zpool status reports no scan until then); tank’s first is due on 1 December 2026.

  • NasBackupPoolCopyStale and NasBackupPoolCopyFailed, once the backup pool exists and nas-replicate.timer has run once.

Fans and the embedded controller#

QTS drives the fans through the TS-253D’s embedded controller. On Ubuntu, the community qnap8528 kernel module exposes it through hwmon: fan speeds, PWM, temperatures, LEDs and buttons. The role builds it with DKMS at a pinned commit (nas_qnap_ec_commit, a release at least two weeks old), loads it with skip_hw_check=true (the TS-253D’s EC reports another chip ID) and DKMS rebuilds it for every new kernel. nas_qnap_ec_driver: false leaves it out.

The module does not decide fan speeds, and on this NAS nothing else needs to: sensors shows the EC running the one fan by itself (qnap8528-isa-0000: fan1 about 1,170 RPM at pwm1 38%, with two EC temperatures), so the role installs no fan curve. Should the EC’s speed ever prove wrong, a curve of our own is a follow-up: pwmconfig, which writes /etc/fancontrol, is interactive, so run it on the NAS by hand and put what it writes into nas_fancontrol_config; the role then installs and enables fancontrol. The module is unsigned, which is fine here: the NAS’s firmware has no Secure Boot.

Restore from the backup pool#

On new hardware (or new SSDs), install and configure as in steps 1 to 3 with the LaCie plugged in, then create only the main pool, so that the datasets do not exist yet:

ansible-playbook pb_nas.yml --tags nas_pool -e nas_create_pool=true -e nas_force=true

On the NAS, send each top-level dataset back from the backup pool, with every snapshot:

for ds in bigdisk k8s-dynamic Minecraft; do
    sudo syncoid --recursive --no-sync-snap "backup/tank/$ds" "tank/$ds"
done

At USB 3 speeds (100 to 150 MB/s from the LaCie), 1.8 TB takes about four hours; k8s-cluster and k8s-dynamic, which the cluster needs first, are small, so send bigdisk/k8s-cluster and k8s-dynamic first if the cluster is waiting. Then run the whole playbook, which sets the datasets’ mountpoints and properties, mounts them and starts the NFS server:

ansible-playbook pb_nas.yml

The nightly copy then carries on incrementally from the snapshots both pools share.

Restore from Drive#

With no backup pool either, run the playbook with -e nas_create_pool=true: it creates the datasets and the cluster’s empty directory tree with the right owners. Then restore the backups, the Minecraft store and worlds, and scrap from Drive as Off-site copy to Google Drive describes. The media library, the photo archive and the other shares are not in the cluster’s off-site copy (the photo archive has its own copy on Drive).
