Expose Cluster Ports Through a VPS Relay#

The vps-relay service publishes chosen cluster ports on the fixed public IP of a VPS. Use it when the cluster cannot accept inbound connections, for example because the home connection is behind ISP carrier-grade NAT (CGNAT), or when you do not want to publish your home IP. Minecraft game ports are the first user; any TCP or UDP service can be added as one more list entry.

The Cloudflare tunnel (Expose Web Services via Cloudflare Tunnel) already covers HTTP(S) services. The relay is for protocols the tunnel cannot carry.

How it works#

player ──► VPS public :port ──► frps ◄══ tunnel opened BY the cluster, over the tailnet ══ frpc ──► target:port

  • The vps-relay Deployment runs two containers in one pod:

    • tailscale joins your tailnet as an ephemeral node tagged tag:vps-relay, in userspace mode (no NET_ADMIN, no /dev/net/tun, no hostNetwork). It exposes a SOCKS5 proxy on 127.0.0.1:1055 inside the pod.

    • frpc connects through that proxy to frps on the VPS, authenticates with a shared token over TLS, and registers one proxy per forwarded port.

  • frps on the VPS listens for players on each forwarded port and relays each connection back down the tunnel that frpc opened. frpc delivers it to the forward’s target on the same port number.

Every connection is opened from the cluster side. The VPS never initiates a connection into the home network, the tailnet policy gives the VPS no access to the relay node, and the relay node advertises no subnet routes.

Trade-offs#

  • Services see every client as coming from the relay pod, not the client’s real IP. IP-based bans and logs are of no use; name-based controls (such as Minecraft whitelists and ops) still work.

  • The relay depends on Tailscale’s coordination service to set up the tailnet connection between the pod and the VPS.

Prerequisites#

  • A VPS with a public IPv4 address, already on your tailnet (tailscale up).

  • Admin access to your tailnet’s policy file and its OAuth clients.

  • A DNS name you can point at the VPS (for example a grey-cloud Cloudflare record in your cluster domain).

Step 1: Tailnet policy#

Tag the VPS (for example tag:vps). An untagged VPS belongs to your user, so any rule that lets your own devices reach things (autogroup:member, or the default allow-all) would also let the VPS reach the relay. A tagged VPS is a separate identity that you grant nothing. Tagging also stops its key expiring; if you use Tailscale SSH to reach it, your ssh rules must then name the tag.

In the Tailscale admin console, Access controls, merge the following into your policy file:

{
  "tagOwners": {
    "tag:vps":       ["autogroup:admin"],
    "tag:vps-relay": ["autogroup:admin"]
  },
  "grants": [
    // Your own devices keep full access. Tagged devices are not members,
    // so this does not cover the VPS.
    { "src": ["autogroup:member"], "dst": ["*"], "ip": ["*"] },
    // The relay may reach only frps on the VPS.
    { "src": ["tag:vps-relay"], "dst": ["tag:vps"], "ip": ["tcp:7000"] }
    // Deliberately nothing with src tag:vps.
  ],
  "tests": [
    { "src": "tag:vps-relay", "accept": ["tag:vps:7000"], "deny": ["tag:vps:22"] },
    { "src": "tag:vps", "deny": ["tag:vps-relay:1055", "tag:vps-relay:22"] }
  ]
}

The tests are checked on every save, so a later policy edit cannot quietly let the VPS dial in. If your file uses acls rather than grants, the relay rule is {"action": "accept", "src": ["tag:vps-relay"], "dst": ["tag:vps:7000"]}.

Then apply the tag on the VPS (or in the console, Machines → ⋯ → Edit ACL tags):

sudo tailscale up --advertise-tags=tag:vps --reset

--reset also clears any other tailscale up options you set earlier, such as --ssh or --accept-routes. Add them back on the same command, or use the console instead.

Warning

A new tailnet starts with an allow-all rule ("src": ["*"], "dst": ["*"]). While that rule is present, every device on the tailnet, including the VPS, can reach the relay node. Remove it; the autogroup:member grant above replaces it for your own devices. The relay advertises no routes, so even then the VPS cannot reach the rest of your home network through it.

Step 2: OAuth client#

The pod authenticates with an OAuth client secret. Unlike auth keys, which expire after at most 90 days, OAuth clients do not expire.

  1. In the admin console go to Settings → OAuth clients → Generate OAuth client.

  2. Grant the Auth Keys scope with Write access, and add the tag tag:vps-relay.

  3. Generate the client and copy the client secret (tskey-client-…). It is shown only once.

The pod appends ?ephemeral=true&preauthorized=true to the secret, so each pod joins as an ephemeral node that Tailscale removes soon after the pod goes away. No Tailscale state is stored in the cluster.

Step 3: Set up frps on the VPS#

scripts/vps-relay-setup does the whole VPS side. It needs Podman 4.4 or newer and Tailscale up on the VPS, and it:

  • writes /etc/frp/frps.toml, with the control port bound to the VPS’s tailnet IP only and allowPorts set to exactly the ports you give it;

  • generates the shared frp token into /etc/frp/frps.env (root-only) on the first run, and prints it once for sealing;

  • installs frps as a Podman Quadlet (/etc/containers/systemd/frps.container), running as an unprivileged user with a read-only root filesystem, and starts it;

  • opens the forwarded ports publicly and the control port on tailscale0 only, with ufw or firewalld if either is active;

  • checks that frps is listening on the tailnet IP.

It is idempotent: re-running it keeps the existing token, replaces only the files that changed, and restarts frps only when something did, so players connected through the relay are not dropped by a no-op run.

The frp control port defaults to 7000. If you change vps_relay.frp_port, run the script with the same value (sudo FRP_PORT=<port> ./vps-relay-setup ...) and change the port in the tailnet grant and tests in Step 1 to match.

In the devcontainer, print the forwards in the form the script takes:

just vps-relay-forwards        # e.g. tcp:30565-30584

Copy the script to the VPS and run it with those arguments:

scp scripts/vps-relay-setup <vps>:
ssh <vps>
sudo ./vps-relay-setup tcp:30565-30584

Save the printed token in your password manager: you need it for Step 4, and again for cluster rebuilds. sudo ./vps-relay-setup --show-token prints it again later.

Also open the forwarded ports in your VPS provider’s cloud firewall, if it has one. Do not open 7000 there.

Step 4: Seal the credentials#

Seal both values into the vps-relay namespace as the vps-relay-credentials Secret. The file name must end in -secret.yaml (singular), because the .gitleaks.toml allowlist only covers that pattern. See Manage Sealed Secrets for background.

# Prompt for both values (not echoed, not stored in shell history)
printf 'Tailscale OAuth client secret: '; read -rs TS_SECRET; echo
printf 'frp token: '; read -rs FRP_TOKEN; echo

kubectl create secret generic vps-relay-credentials \
    --namespace vps-relay \
    --from-literal=ts-oauth-client-secret="$TS_SECRET" \
    --from-literal=frp-token="$FRP_TOKEN" \
    --dry-run=client -o yaml | \
  kubeseal --controller-name sealed-secrets \
    --controller-namespace kube-system -o yaml > \
    kubernetes-services/additions/vps-relay/templates/vps-relay-secret.yaml

unset TS_SECRET FRP_TOKEN

The vps-relay namespace does not need to exist yet.

Tip

For cluster rebuilds, export the two values as VPS_RELAY_TS_OAUTH_CLIENT_SECRET and VPS_RELAY_FRP_TOKEN alongside the other external credentials. scripts/export-external-creds captures them from a running cluster, and just generate-and-seal-all re-seals them when both are set (and skips them when neither is).

Step 5: Configure and enable the relay#

Edit kubernetes-services/values.yaml:

enable_vps_relay: true
vps_relay:
  vps_tailnet_host: 100.x.y.z     # the VPS's tailnet IP or MagicDNS name
  frp_port: 7000
  forwards:
    - name: minecraft
      protocol: tcp
      ports: 30565-30584          # single port or inclusive range
      target: 192.168.1.92        # LAN IP, or an in-cluster Service DNS name

Each forward publishes ports on the VPS and relays them to the same port numbers on target. Because frpc runs inside the cluster, target can be a Service DNS name such as my-svc.my-namespace.svc.cluster.local, so new services do not need a NodePort. protocol is tcp or udp (frp carries UDP over its TCP tunnel).

Commit and push. ArgoCD creates the vps-relay Application and namespace.

Step 6: Point DNS at the VPS#

Create an A record for the public name (for example mc.<domain>) with the VPS’s public IP and the DNS only (grey cloud) proxy status. The address is static, so no DDNS is needed. Cloudflare’s proxy only carries HTTP(S), so the record must not be proxied.

Step 7: Verify#

  1. Pod — both containers are running and the tailscale container is Ready:

    kubectl get pods -n vps-relay
kubectl logs -n vps-relay deploy/vps-relay -c tailscale | tail

  2. Tailnet — on the VPS, tailscale status lists a vps-relay node (or vps-relay-1 and so on, until Tailscale removes an earlier ephemeral node after a pod restart) tagged tag:vps-relay.

  3. frpc — each forwarded port logs start proxy success:

    kubectl logs -n vps-relay deploy/vps-relay -c frpc | grep -c 'start proxy success'

  4. Public port — from outside your network (an online port checker, or nc -vz <vps-public-ip> 30565), a forwarded port is open while its target is listening.

  5. Direction — the VPS cannot open a connection to the relay node. On the VPS, nc -vz -w 5 <relay-tailnet-ip> 22 must time out: the policy drops the packets. A prompt connection refused means the policy still lets the VPS reach the node (see the warning in Step 1).

Adding a forward#

  1. Add an entry to vps_relay.forwards. Names must be unique.

  2. On the VPS, re-run scripts/vps-relay-setup with the new list from just vps-relay-forwards. It updates allowPorts, restarts frps and opens the ports. Firewall rules for ports you have removed are left in place; close them by hand.

  3. Commit and push. The ConfigMap checksum changes, so the pod restarts with the new frpc.toml.

Important

Step 2 is a deliberate manual sync point. A forward in git does nothing until the VPS allows its ports, so a mistaken or malicious change to the repository cannot publish a new port on its own. frpc logs port not allowed for a forward the VPS has not yet allowed.

Troubleshooting#

The pod is stuck in CreateContainerConfigError#

The vps-relay-credentials Secret does not exist. The SealedSecret is missing, or was sealed for another cluster or namespace.

The tailscale container never becomes Ready#

Check its log. requested tags [tag:vps-relay] are invalid or not permitted means the OAuth client does not have the tag, or tagOwners does not define it. An authentication error means the client secret is wrong or was revoked.

frpc logs connect to server error#

  • i/o timeout or connection refused through the SOCKS proxy: the tailnet policy does not grant tag:vps-relay access to the VPS on the frp port, frps is not running, or it is bound to a different address.

  • token in login doesn't match: the sealed frp-token differs from FRP_AUTH_TOKEN on the VPS.

frpc retries on its own, so a relay started before the VPS is ready recovers without a restart.

Rotating the credentials#

Re-seal vps-relay-credentials as in Step 4 and push. The pod reads the Secret only when it starts, so the new values take effect at its next restart. If you rotated the frp token, update /etc/frp/frps.env on the VPS to match (or delete it and re-run scripts/vps-relay-setup, which generates a new token for you to seal).

The public port is closed#

  • Check allowPorts and both firewalls on the VPS; re-running scripts/vps-relay-setup with the current forwards fixes the first two.

  • On the VPS, sudo journalctl -u frps -n 20 shows why frps refused a proxy.

  • Check the forward’s target from inside the cluster, for example kubectl run -it --rm nc --image=busybox -- nc -vz <target> <port>.

Removing the relay#

Set enable_vps_relay: false and push. ArgoCD prunes the namespace’s resources and the ephemeral tailnet node disappears shortly afterwards. Then, on the VPS, run sudo systemctl stop frps, delete /etc/containers/systemd/frps.container and /etc/frp/, and close the firewall ports. Finally delete the DNS record and revoke the OAuth client.
