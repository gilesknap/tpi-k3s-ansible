Back up and recover the router#

The home router is a MikroTik hEX S (RouterBOARD 760iGS, MediaTek MT7621) running OpenWrt 23.05.5, at 192.168.1.1 (dns_router in group_vars/all.yml). It carries every household device’s traffic and DNS, not only the cluster’s. This page covers its daily backup, changing it with a revert that fires by itself unless the change is confirmed, restoring it with a playbook, and getting it back when SSH to it is gone. Its DNS and DHCP configuration is code: Manage the router’s DNS and DHCP.

pb_router.yml reaches the router as the router host in hosts.yml (user and address from dns_router), with raw, as it has no Python. Every play in it is tagged never, so a run names one with --tags. In the Claude sandbox, add --private-key /root/.config/claude-ssh/id_ed25519 to each ansible-playbook command on this page.

A backup is a sysupgrade -b tarball: everything under /etc/config/, /etc/passwd, /etc/shadow (the root password hash), the Dropbear host keys and authorized_keys, the LuCI TLS key, and the PPPoE login of the WAN in /etc/config/network. (The hEX S has no Wi-Fi radio, so there are no Wi-Fi keys.) It is only ever stored encrypted, and never goes in the repository, decrypted or not.

How the backup runs#

The etcd_backup role installs a second timer next to the etcd backup on the control plane (node02), router-backup.timer. Every day at 23:00 Europe/London it:

  1. connects to the router as root with its own SSH key, /etc/k3s-etcd-backup/router_ed25519, which never leaves node02. The router accepts that key for one command only: its line in /etc/dropbear/authorized_keys (Dropbear does not read /root/.ssh) starts command="sysupgrade -b -",no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty, so whatever node02 asks for, the router runs sysupgrade -b -. The router’s host key is pinned in /etc/k3s-etcd-backup/router_known_hosts; the role reads it from the router over the connection Ansible already trusts;

  2. holds the tarball in RAM (/run), checks it lists etc/config/network, and encrypts it with age to etcd_backup_age_recipient, the key every backup uses;

  3. copies it to the NAS as /bigdisk/k8s-cluster/backups/router/router-<UTC time>.tar.gz.age, checks the copy’s checksum, and keeps the newest 30;

  4. writes router_backup_* metrics for node-exporter.

The two jobs share a lock, so they never use the NAS mount at once. The off-site jobs copy backups/router/ to Google Drive and B2 each morning with the rest of backups/ (Off-site copy to Google Drive). The alerts RouterBackupFailed, RouterBackupStale, RouterBackupNeverSucceeded and RouterBackupMetricsMissing (additions/grafana/router-backup-rules.yaml) reach the phone through ntfy.

The role authorizes the key on the router with raw (the router has no Python), adding the line only if it is missing. If the control plane moves, or is re-flashed (a new key), the old line stays, still limited to sysupgrade -b and harmless; delete it by hand if you like (Recover the control plane).

Set it up#

Done once, and again only on a new NAS or a new control plane:

ansible-playbook pb_nas.yml --tags nas_datasets   # creates backups/router, owned by 65534
ansible-playbook pb_all.yml --limit node02 --tags etcd_backup
just router-backup

Back up now#

pb_router.yml --tags change (below) runs this first itself. Run it before any other change to the router, over SSH by hand or in LuCI:

just router-backup

It starts the same service on the control plane, waits for it and prints its log and metrics. To list the backups:

ssh nas sudo ls -l /bigdisk/k8s-cluster/backups/router

Change the router safely#

A bad firewall, network or DNS change can cut the internet for the whole house, and with it the SSH session that made it. LuCI rolls an unconfirmed change back after 90 seconds; changes over SSH get the same from pb_router.yml --tags change:

ansible-playbook pb_router.yml --tags change -e router_change_tasks=<name>

  1. Backup off the router. It starts router-backup.service on node02, as just router-backup does, and stops unless it succeeds: an encrypted copy from just before the change is on the NAS.

  2. Snapshot on the router. sysupgrade -b /tmp/router-guard/backup.tar.gz, in RAM. Creating /tmp/router-guard is also the lock: a second run while a guard is armed fails there, rather than snapshot the state the first one guards against.

  3. Arm the revert. A watchdog on the router, started with start-stop-daemon -b -m -p /tmp/router-guard/pid, sleeps router_guard_timeout seconds (default 300, -e router_guard_timeout=<s> to change it), then, if the snapshot is still there, logs router-guard to syslog, runs sysupgrade -r on the snapshot and reboots. start-stop-daemon -b forks, calls setsid, points stdin, stdout and stderr at /dev/null and forks again, so the watchdog is a child of init in a session of its own, with no terminal: the SSH session ending, or dying with the network, does not reach it. The play prints the time the revert fires (controller time).

  4. The change: the task file roles/router/tasks/<name>.yml, e.g. dhcp, which pushes the router’s DNS and DHCP from a template (Manage the router’s DNS and DHCP). With no router_change_tasks the play skips this and only arms, checks and disarms, a harmless test of the guard.

  5. The checks, from the controller (roles/router/tasks/check.yml):

    • the internet answers: HTTPS to router_check_url (https://github.com);

    • the router’s DNS answers a public name (host -t A github.com 192.168.1.1);

    • k3s.lan (k3s_api_name) resolves via the router to node02’s lan_ip in hosts.yml (192.168.1.82);

    • node02.lan (control_plane in the lan domain) resolves via the router to the same address: a static name, served from the router’s DHCP configuration (Manage the router’s DNS and DHCP);

    • the cluster API answers on port 6443 (any HTTP status: anonymous requests get 401);

    • a new SSH login to the router works.

  6. Confirm or revert. Only if every check passes does the play disarm the watchdog (start-stop-daemon -K) and delete /tmp/router-guard. If the change or a check fails and SSH to the router still works, the play runs the revert at once (sysupgrade -r on the snapshot, then a reboot), waits for the router to come back, and fails, naming the check. If SSH fails too, it fails saying when the router will revert by itself, and the router does so on time. Either way the internet is down for a minute or two while it reboots; afterwards run the checks again (below).

A change step may reload networking or the firewall and drop its own SSH session: that is fine, the play carries on to the checks, and they decide. A change that silently drops packets leaves a step waiting until SSH’s keepalive gives up, about a minute (ServerAliveInterval=15, ServerAliveCountMax=4 for the routers group in hosts.yml); then the checks run and fail, and the play reverts or reports the deadline as above.

If the play is stopped (Ctrl-C) while the guard is armed, the router still reverts at the deadline. To keep the change instead, disarm it by hand:

ssh root@192.168.1.1 'start-stop-daemon -K -p /tmp/router-guard/pid; rm -rf /tmp/router-guard'

The same rm -rf /tmp/router-guard clears a stale lock left by an arm that failed after creating it (a failed sysupgrade -b), which otherwise makes the next run fail at mkdir; a reboot clears it too.

The snapshot only unpacks over /, as a restore does: a change that adds files (a new /etc/nftables.d/*.nft) leaves them behind after a revert, so a change edits the existing /etc/config/* files rather than add new ones. A power cut while the guard is armed clears the snapshot and the watchdog with the rest of RAM, and the router boots with the change; the backup on the NAS from step 1 is the way back then.

Check the router#

The checks of step 5, on their own, change nothing:

ansible-playbook pb_router.yml --tags check

Drill the revert#

Push the DNS and DHCP template once first (just router-dhcp, Manage the router’s DNS and DHCP): until then the drill’s reboot loses the .lan names, and the <control_plane>.lan check fails for hours although the guard worked.

Proves the guard on the real router. It arms the guard, writes a note into the router’s system settings (uci set system.@system[0].notes='router-guard drill <time>', committed), deliberately does not confirm it, waits for the watchdog to restore the snapshot and reboot the router, then checks the note is gone and runs the checks, retrying the internet and DNS checks for up to two minutes while the WAN comes back:

ansible-playbook pb_router.yml --tags drill

It takes router_guard_timeout (5 minutes) plus the reboot, and the internet is down for everyone for a minute or two during the reboot. -e router_guard_timeout=60 makes it shorter.

Restore with the playbook#

For a router that still answers SSH, e.g. after a bad change.

  1. Copy the backup off the NAS and decrypt it with the offline age key (where it is kept: 2. Decrypt it below):

    f=$(ssh nas sudo ls /bigdisk/k8s-cluster/backups/router | grep '\.age$' | tail -n 1)
ssh nas sudo cat "/bigdisk/k8s-cluster/backups/router/$f" > "$f"
(umask 077; age -d -i ~/k3s-etcd-backup.agekey "$f" > /dev/shm/router.tar.gz)

  2. Restore it:

    ansible-playbook pb_router.yml --tags restore -e router_restore_file=/dev/shm/router.tar.gz

    It lists the files in the backup and asks you to type yes (anything else stops it). Ansible’s script module then copies the file into a temporary directory in the router’s /tmp (RAM), runs sysupgrade -r on it and deletes the directory. The play reboots the router and waits for its SSH to come back. The internet is down for everyone for a minute or two.

  3. Delete /dev/shm/router.tar.gz.

The backup holds the router’s own host keys and authorized_keys, so SSH works afterwards as before.

A restore only unpacks the tarball over /: files added since the backup (a new /etc/nftables.d/*.nft or /etc/config/*) stay. To undo a bad change that added files, reset the saved configuration first with firstboot -y and a reboot (as in failsafe, below), then restore.

An older backup also brings back its authorized_keys. If the control plane has been rebuilt since, its backup key is not in them: rerun ansible-playbook pb_all.yml --limit node02 --tags etcd_backup afterwards to authorize it again.

When SSH to the router is gone#

When a bad firewall, network or Dropbear change locks everyone out, use OpenWrt’s failsafe mode: a boot that ignores the saved configuration, brings up only the first LAN port at 192.168.1.1, and runs SSH with no password. Nothing in it needs the internet, but this does need a laptop with ssh, age and the age key, and a network cable.

1. Get the backup and the key while you can#

Do this first: once the laptop is cabled to the router alone, it reaches nothing else.

  • The newest backup is on the NAS (gknas, 192.168.1.3), in /bigdisk/k8s-cluster/backups/router/, 0600 to 65534, so it needs sudo. With the router down there is no DHCP: give the laptop a static address on the LAN, e.g. 192.168.1.250/24, then copy it as in the playbook restore above. Whether the NAS answers depends on what broke: the router’s LAN bridge, or a switch between the laptop and the NAS, still carries the traffic if only the router’s own services are gone.

  • If the NAS cannot be reached, the same files are off site, which needs the internet (a phone’s hotspot): Google Drive home-cluster-offsite/backups/router/, or the B2 bucket gk-cluster-offsite/backups/router/ (Second off-site copy: Backblaze B2). The files are as on the NAS (already .age, uploaded as they are).

  • An older backup, if the newest already holds the bad change: they are named by UTC time, newest last; pick the one from before it.

2. Decrypt it#

The age private key is offline, not on the cluster: the owner’s ~/k3s-etcd-backup.agekey, kept in two places (Backup and restore, “One-time setup”), and the first page of the paper kit (Print the paper recovery kit), which can be typed into key.txt (age-keygen -y key.txt must print etcd_backup_age_recipient). The laptop needs age already installed: with the internet down it cannot fetch it (the devcontainer has it).

(umask 077; age -d -i ~/k3s-etcd-backup.agekey router-<time>.tar.gz.age > /dev/shm/router.tar.gz)
tar -tzf /dev/shm/router.tar.gz   # etc/config/network, etc/shadow, ...

3. Boot the router into failsafe mode#

The hEX S has two LEDs besides the port lights: the blue power LED, which OpenWrt uses for boot and failsafe, and a blue SFP link LED. It has two buttons, reset and mode. During boot OpenWrt waits 2 seconds for a button press; any button press then enters failsafe.

  1. Set the laptop to the static address 192.168.1.2/24 (no gateway) and cable it to port 2 of the router, the first LAN port: failsafe brings up only that one (port 1 is the WAN; ports 3 to 5 stay off). Unplug whatever else was in port 2.

  2. Pull the router’s power, and plug it back in. Do not hold reset while plugging in: before OpenWrt starts, the button belongs to MikroTik’s RouterBOOT bootloader, which uses a press at power-on to boot its backup loader or to wait for a Netinstall over the network instead of starting OpenWrt. (What RouterBOOT does on this exact board with each hold time is not verified here; avoid it.)

  3. Watch the power LED. When OpenWrt’s preinit starts it blinks fast (about 5 times a second): press and release reset then, within 2 seconds. Pressing it a few times during the fast blinking is fine.

  4. In failsafe the LED blinks faster still (about 10 times a second) and keeps blinking. If it settles into a slower blink (about 2.5 times a second), the window was missed and the router is booting normally: go back to step 2.

Once the router is up normally, do not hold reset for 5 seconds or more: on release that is a factory reset (/etc/rc.button/reset runs jffs2reset). A short press reboots it.

4. Restore from failsafe#

Failsafe makes new host keys in RAM and has no root password, so skip the known_hosts check for this session only:

ssh -o UserKnownHostsFile=/dev/null -o StrictHostKeyChecking=no root@192.168.1.1 \
    'cat > /tmp/router.tar.gz' < /dev/shm/router.tar.gz
ssh -o UserKnownHostsFile=/dev/null -o StrictHostKeyChecking=no root@192.168.1.1

On the router:

mount_root                         # mount the saved configuration (the overlay) read-write
sysupgrade -r /tmp/router.tar.gz   # unpacks the backup over /
sync
reboot -f

sysupgrade -r only unpacks the tarball over /, as tar -C / -xzf /tmp/router.tar.gz would, so files added since the backup stay (see “Restore with the playbook”; firstboot -y below clears them). As there, an older backup may need the control plane’s backup key authorized again. The router boots with the restored configuration, its own host keys and authorized_keys; set the laptop back to DHCP and check the internet, DNS (k3s.lan resolves) and ssh root@192.168.1.1.

If the router still does not come up right (the overlay itself is damaged, or the backup holds the fault), go back into failsafe and reset to defaults instead, then restore an older backup:

firstboot -y    # erases the saved configuration: OpenWrt defaults, 192.168.1.1, no root password
reboot -f

After that reboot the router has OpenWrt’s default configuration: LAN on ports 2 to 5 at 192.168.1.1 with DHCP, no WAN login, no root password and new host keys. Restore an older backup into it with the same two ssh commands as above, without mount_root, then reboot; or upload it in LuCI (http://192.168.1.1), System > Backup / Flash Firmware > Restore backup.

Delete /dev/shm/router.tar.gz when done, and run just router-backup once the cluster is back.
