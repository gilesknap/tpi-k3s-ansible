Services reference#

Everything ArgoCD runs on the cluster, plus ArgoCD itself: where each service comes from, which version is pinned, how it is reached and who may use it. The live cluster has 27 Applications: the root all-cluster-services and the 26 children it renders from kubernetes-services/templates/. Versions here are the pins in those templates and in kubernetes-services/values.yaml; when this page and the code disagree, the code is right.

Service catalogue#

Placement says where the pods run today and what decides it. “Any worker” means node03, node04, nuc1 or nuc2: node02 is tainted NoSchedule for the control plane and ws03 workstation=true:NoSchedule, so only pods that tolerate those taints land there. node03, the warm-standby control plane, carries a PreferNoSchedule taint: the scheduler uses it when a spread or anti-affinity rule asks for a second node, and otherwise prefers the others.

ArgoCD itself#

ArgoCD is not in kubernetes-services/templates/. The cluster Ansible role installs it with Helm from oci://ghcr.io/argoproj/argo-helm/argo-cd, chart 9.4.17 (ArgoCD v3.3.6), into the argo-cd namespace (roles/cluster/tasks/argocd.yml), then applies the AppProject kubernetes and the root Application from argo-cd/. One replica of each component, on any worker.

  • Login: GitHub through its bundled Dex. The built-in admin account is disabled (admin.enabled: "false").

  • RBAC: configs.rbac maps each of admin_emails to role:admin; policy.default is role:readonly.

  • Dex clients: argo-cd, argocd-monitor and grafana, so Grafana and argocd-monitor log in through the same Dex.

  • AppProject: sourceRepos is an allow-list of this repository and the chart registries in the tables above (argo-cd/argo-project.yaml). A new chart source must be added there and applied with ansible-playbook pb_all.yml --tags cluster.

GitOps delivery with ArgoCD describes the app-of-apps layout.

Service details#

Sealed Secrets#

Bitnami’s controller, in kube-system. It decrypts each SealedSecret in Git into a Secret. See Manage Sealed Secrets.

cert-manager#

Issues one wildcard certificate, *.gkcluster.org and gkcluster.org, from Let’s Encrypt by DNS-01 through the Cloudflare API, into the Secret cert-manager/wildcard-tls. The Gateway’s HTTPS listener serves it for every host, so no route needs its own. Requests 50m/128Mi, limits 200m/256Mi.

Additional manifests: additions/cert-manager/templates/

  • cloudflare-api-token-secret.yaml: SealedSecret with the DNS API token (cert-manager’s DNS-01 token)

  • issuer-letsencrypt-prod.yaml: the letsencrypt-prod ClusterIssuer

  • wildcard-certificate.yaml: the wildcard Certificate

Its metrics are scraped by a ServiceMonitor in additions/grafana/, and certificate expiry alerts come from there (Monitoring and alerts).

Cilium’s Gateway#

The only ingress: the Gateway web in gateway (GatewayClass cilium-gateway), served by Cilium’s Envoy, the cilium-envoy DaemonSet in kube-system, so it runs on every node and a reboot or drain leaves the rest serving. Its Service, cilium-gateway-web, takes plain HTTP from cloudflared on port 80 and serves the wildcard certificate on 443; ServiceLB publishes both on the node addresses. See Check Cilium’s Gateway and ADR 16.

Most HTTPRoutes are rendered by the small additions/ingress/ chart, which the service templates include as a source with name, service_name, service_port and oauth2_proxy.

oauth2-proxy#

GitHub login gate for the services with no login of their own: Headlamp, Alertmanager, the Minecraft dashboard, scrap and the Hubble UI. The Gateway asks it about every request (the routes’ ExternalAuth filter) and it admits only admin_emails. Two replicas; sessions live in the encrypted cookie on .gkcluster.org, so the replicas share no state. Requests 10m/64Mi, limits 100m/128Mi.

Additional manifests: additions/oauth2-proxy/

  • oauth2-proxy-secret.yaml: SealedSecret with the GitHub OAuth credentials

  • error-templates.yaml: the error page shown to an account that is not allowed

See Set up OAuth authentication.

cloudflared#

The outbound Cloudflare Tunnel connector. Two replicas on different nodes (required anti-affinity) with maxUnavailable: 1; non-root, read-only root filesystem. The tunnel, its routes and its DNS records are code in cloudflare/; the pod only needs the tunnel token.

Additional manifests: additions/cloudflared/

  • deployment.yaml: the Deployment and its PodDisruptionBudget

  • networkpolicy.yaml: the pod’s NetworkPolicy

  • tunnel-secret.yaml: SealedSecret with the tunnel token (just cf-seal-tunnel-token)

See Manage Cloudflare: DNS, tunnel and Access and Networking and ingress.

CoreDNS HA#

K3s owns the CoreDNS Deployment and re-applies it at every server restart, so this Application does not replace it. It adds an HPA with minReplicas and maxReplicas both 2, which holds the Deployment at two replicas, and a PodDisruptionBudget. See Automatic maintenance.

local-storage and nfs-csi#

local-storage defines the local-nvme class and one static, node-pinned PV per entry of local_storage in values.yaml: Prometheus and Grafana on node04, Jellyfin and scrap’s backup copy on nuc2. It also marks K3s’s local-path class as not the default.

nfs-csi provides the two dynamic classes on the NAS: nfs-stable (the default; one fixed folder per claim under /k8s-dynamic/stable, archived on delete) and nfs-rwx (a scratch folder per volume under /k8s-dynamic, deleted with the claim).

See Storage and Stable NFS volumes.

kernel-settings#

A DaemonSet that raises net.core.rmem_max and net.core.wmem_max to 7500000 on the nodes it runs on, for network buffers.

kured and system-upgrade-controller#

The nightly maintenance pair. kured reboots a node when /var/run/reboot-required exists, between 02:30 and 05:00 Europe/London, one node at a time, after draining it; it runs on node02 but not on ws03, and skips a node that is running a K3s upgrade Job. system-upgrade-controller applies K3s patch releases of the k3s.minor line (v1.34) between 01:00 and 02:00 through two Plans (additions/k3s-upgrade-plans/), which exclude ws03.

The controller’s manifests are vendored unchanged from its GitHub release in additions/system-upgrade-controller/, so a sync or rebuild does not depend on GitHub downloads. To upgrade it, re-download both files and update the version and sha256 sums as the kustomization.yaml header there describes.

See Automatic maintenance and Upgrade K3s.

backups#

CronJobs that write to /bigdisk/k8s-cluster/backups on the NAS through the static k8s-cluster-nfs volume: Grafana’s database daily and weekly (on node04), Jellyfin’s database and config daily and weekly (on nuc2), and offsite-backup, which at 05:30 uploads every backup, age-encrypted, to the Google Drive folder home-cluster-offsite, and, once enabled, offsite-backup-b2, which uploads the NAS backups to a Backblaze B2 bucket with Object Lock. scrap’s backups are CronJobs of its own chart, and etcd’s is a systemd timer on node02. See Backup and restore.

Grafana + Prometheus (kube-prometheus-stack)#

Prometheus, Grafana, Alertmanager, the operator, kube-state-metrics and node-exporter, with this cluster’s alert rules and the Alertmanager to ntfy route. Synced with ServerSideApply=true because of the size of its CRDs. See Monitoring and alerts.

Headlamp#

Kubernetes dashboard behind oauth2-proxy. After the GitHub login, paste a ServiceAccount token (just headlamp-token); the chart binds the headlamp ServiceAccount to cluster-admin. Requests 50m/128Mi, limits 200m/256Mi.

The Argo CD plugin adds a sidebar section listing Applications with sync and health status and buttons to sync or refresh. It drives the Kubernetes API, not the ArgoCD API, so it needs no ArgoCD credentials. The plugin is not on ArtifactHub, so templates/dashboard.yaml adds an init container that downloads the release tarball, verifies its SHA-256 and unpacks it into an emptyDir. Bump headlamp.argocd_plugin.version and sha256 together; set enabled: false to drop it.

argocd-monitor#

A dashboard of Application status from epics-containers/argocd-monitor, with links from each workload to its Grafana dashboard. It logs in through Dex with its own oauth2-proxy sidecar (client argocd-monitor, SealedSecret argocd-monitor-oauth) and talks to argocd-server inside the cluster. Pinned to amd64 nodes.

home#

nginx serving a static landing page from a ConfigMap, with a card per web UI and the LAN and tailnet probes described under Access.

echo#

ealen/echo-server: returns the request it received as JSON, which shows the headers that Cloudflare and the Gateway’s Envoy add. Non-root with a read-only root filesystem.

ntfy#

Self-hosted push notifications at ntfy.gkcluster.org, locked down: auth-default-access: deny-all, no sign-up, no web app, no attachments. Users, tokens and access are declarative, from the ntfy-auth SealedSecret and the chart’s values: write-only senders (alertmanager and scrap on cluster-alerts, vps on vps-alerts) and a read-only phone user. It is public through the tunnel with a bypass Access application, because the phone app cannot log in to Access, and a Cloudflare rate-limiting rule. Its network policies admit only the Gateway, the Alertmanager pods and the scrap pods. See Push notifications with ntfy.

scrap#

Personal knowledge store (gilesknap/scrap). The pod runs on any node: the database is on an emptyDir, replicated by Litestream to a static NFS volume on the NAS. The web UI is behind Cloudflare Access and oauth2-proxy; /mcp has its own HTTPRoute behind a Cloudflare service token and scrap’s bearer token; public pages are served from the scrap-public namespace at pages.gkcluster.org. See Run scrap.

Jellyfin#

The upstream chart, pinned to nuc2 for its config volume (a local-nvme PV at /home/k8s-data/jellyfin) and the Iris Xe (see Intel GPU device plugin). hostNetwork, so it answers on nuc2’s port 8096 on the LAN and the tailnet; no HTTPRoute and no Cloudflare route. The library is a read-only NFS mount of /bigdisk/media. See Run Jellyfin.

Minecraft dashboard#

The OCI chart from gilesknap/k3s-minecraft: an admin UI that installs one itzg Minecraft Helm release per world in its own namespace, each with an nfs-stable claim and a NodePort from 30565 to 30584 on nuc2. Players come in through the VPS relay. See Run the Minecraft dashboard.

VPS relay#

One pod with two containers: a Tailscale userspace sidecar that joins the tailnet as an ephemeral node tagged tag:vps-relay, and frpc, which dials frps on the VPS through it. Each entry in vps_relay.forwards publishes its ports on the VPS’s public address and relays them to the same ports on its target; today that is the minecraft forward, 30565 to 30584 to nuc2. Every connection is outbound from the cluster. Both containers are non-root with a read-only root filesystem and no service-account token. See Expose cluster ports through the VPS relay.

NVIDIA device plugin#

DaemonSet that advertises ws03’s GPU as nvidia.com/gpu. It schedules on nodes labelled nvidia.com/gpu.present=true, which the k3s Ansible role sets for hosts with nvidia_gpu_node: true in hosts.yml, and tolerates the workstation taint. A pod that wants the GPU must tolerate that taint too.

The node needs the NVIDIA container runtime in K3s’s containerd: the update_packages role writes a config.toml.tmpl that makes it the default runtime and survives k3s-agent restarts.

Intel GPU device plugin#

DaemonSet from intel-device-plugins-for-kubernetes that advertises nuc2’s Iris Xe as the gpu.intel.com/i915 resource, so a pod gets /dev/dri for VAAPI or Quick Sync through a resource request instead of running privileged. It schedules on nodes labelled intel.feature.node.kubernetes.io/gpu=true, which the k3s Ansible role sets for hosts with intel_gpu_node: true in hosts.yml. That is the label Node Feature Discovery would set, so NFD could replace the inventory flag later without changing the plugin.

It is the upstream release’s plain DaemonSet, vendored in additions/intel-gpu-plugin/upstream/ so that a sync never fetches from GitHub, with a kustomize patch for the node selector, a toleration of the workstation taint and -shared-dev-num. It needs neither the Intel operator nor cert-manager. -shared-dev-num sets how many pods may share each GPU; it is 1, and Jellyfin holds that one, so raise it before running a second GPU pod. Like any DaemonSet pod it is not evicted when kured drains the node, and it has no PodDisruptionBudget, so it never blocks a reboot.

The i915 kernel driver ships with Ubuntu, so the node needs no extra packages.

Requesting the GPU:

resources:
  limits:
    gpu.intel.com/i915: 1

The plugin mounts the node’s /dev/dri/card* and /dev/dri/renderD* into the container. On nuc2 the render node is root:render, mode 0660, so a non-root container carries the node’s render group ID in supplementalGroups, as Jellyfin does. Look it up on the node with getent group render: it is allocated dynamically and can change across an OS release upgrade. (In the live Jellyfin pod the device nodes show as owned by the pod’s own uid and gid, so the group is a second line of access there.)

securityContext:
  supplementalGroups: [992] # nuc2's render GID

Verifying: check the node advertises the resource, then query VAAPI from the Jellyfin pod, which holds the GPU, with the vainfo bundled in its image:

kubectl get nodes -o custom-columns='NODE:.metadata.name,I915:.status.allocatable.gpu\.intel\.com/i915'
kubectl -n jellyfin exec deploy/jellyfin -- sh -c \
  'ls -l /dev/dri && /usr/lib/jellyfin-ffmpeg/vainfo --display drm --device /dev/dri/renderD128'

vainfo lists the iHD driver and its VAProfile... entrypoints. If the render node has another number, use the one ls printed.
