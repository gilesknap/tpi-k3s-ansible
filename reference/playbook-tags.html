Playbook tags reference#

pb_all.yml is the one playbook that builds and updates the cluster. Each of its plays carries a tag, so a single stage, or a few, can be run on their own. Run it in the devcontainer, from the repo root.

Running individual stages#

# Single stage
ansible-playbook pb_all.yml --tags tools
ansible-playbook pb_all.yml --tags k3s

# Multiple stages
ansible-playbook pb_all.yml --tags k3s,cluster

# Skip a stage
ansible-playbook pb_all.yml --skip-tags flash

Common tag combinations#

Command

Use case

--tags tools

Refresh the CLIs and kubeconfig in the devcontainer (also run when the devcontainer is created)

--tags known_hosts,servers,k3s --limit nuc1

Bring one node up to date, or join a new one

--tags servers

Apply package updates to every node; kured reboots them in its nightly window

--tags k3s,cluster -e k3s_force=true

Reinstall K3s and redeploy every service

--tags cluster

Reinstall ArgoCD’s config, taints and root Application only (what just switch-branch runs)

-e do_flash=true

The whole playbook, flash included (no tag needed)

Using --limit#

Restrict which hosts are targeted:

# Single node
ansible-playbook pb_all.yml --limit node03 --tags k3s -e k3s_force=true

# Turing Pi BMC + specific node (needed for flash)
ansible-playbook pb_all.yml --limit turingpi,node03 -e flash_force=true

# Only the nodes outside the Turing Pi (ws03, nuc1, nuc2)
ansible-playbook pb_all.yml --limit extra_nodes --tags known_hosts,servers,k3s

# The local PV directories on nuc2
ansible-playbook pb_all.yml --limit nuc2 --tags k8s_data_dirs

Note

When using --limit with the flash tag, always include the BMC (turingpi), because the flash role runs on the BMC, not on the node itself. An RK1 flash is only complete after the servers tag’s move_fs has installed its NVMe, so for an RK1 run the whole playbook (or at least --tags flash,known_hosts,servers), not --tags flash alone.

Standalone playbooks#

Playbook

Purpose

Flags

pb_all.yml

Builds and updates the cluster: every stage above

Tags, --limit, and the -e overrides in Variables reference

pb_add_nodes.yml

Gives Ansible control of a machine in extra_nodes whose OS was installed by hand: creates the ansible account, authorises pub_keys/ansible_rsa.pub and adds passwordless sudo. Safe to re-run

--limit <node> -e ansible_user=<existing user> -K. It must be -e, not -u: the inventory sets ansible_user to an account that does not exist on the machine yet

pb_nas.yml

Configures the NAS (gknas, Ubuntu Server + ZFS): imports or, only when asked, creates its pools, then its datasets, NFS exports, snapshots, the nightly copy to the backup pool and health checks (Build or rebuild the NAS (Ubuntu Server + ZFS)). Runs only on the nas group. Tags: known_hosts, nas, and within it nas_os, nas_fan, nas_pool, nas_datasets, nas_nfs, nas_snapshots, nas_health, power_key

None for a normal run, which never creates a pool. -e nas_create_pool=true / -e nas_create_backup_pool=true create one (destroying its disks’ contents), and -e nas_force=true allows disks that are not blank

pb_decommission.yml

Tears the whole cluster down, in order: stops the etcd backup timer, stops ArgoCD reconciling, scales down workloads and deletes chart-owned PVCs, removes ArgoCD and the namespaces, removes the systemd units this repo adds beside K3s, uninstalls K3s (workers, then the control plane) and cleans up node state. Idempotent

None by default: /home/k8s-data (nuc2) and /var/lib/k8s-data (RK1s) are kept, as is everything on the NAS. -e wipe_local_data=true also deletes those two directories, and with them every local-nvme PV’s data

pb_decommission.yml is the first half of a rebuild (Re-flash and rebuild, or the /rebuild-cluster command). It is not the way to remove one node: Node operations covers that.

Ad-hoc commands#

Run Ansible modules directly without a playbook:

# Ping all nodes
ansible all_nodes -m ping

# Run a shell command
ansible all_nodes -a "uptime" --become

# Run a single role
ansible all_nodes -m include_role -a name=known_hosts
